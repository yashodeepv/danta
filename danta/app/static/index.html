Danta Grammar Reference

A Danta spec is a plain-text Markdown file that compiles deterministically to Python, JavaScript, and Java. This reference covers every keyword and construct the compiler recognises.

Overview

The compiler reads the file in one pass: layout first (which section each line belongs to, step nesting, numbering), then semantics (types, name resolution, IR2 validity). Every error is reported against the spec line that caused it.

Sections, in fixed order:

  1. Spec: danta/0.1 — version line, always first
  2. # System: <name> — system declaration + description
  3. ## Constants — named values (optional)
  4. ## Entities — data shapes (optional)
  5. ## Services — external service signatures (optional)
  6. ## Flow: <name> — one or more flows
  7. ## Screen: <name> — UI screens (optional, after flows)

Constants, Entities, and Services must all appear before the first ## Flow:. Lines starting with > are ignored anywhere — use them for inline comments.

Spec Header

Every spec starts with two mandatory declarations.

Version line

Must be the very first non-blank line:

Spec: danta/0.1

System declaration

# System: shop-orders
Takes orders over HTTP, charges them and confirms them.
ElementPatternNotes
# System: <name>[a-z][a-z0-9_-]*Lowercase, hyphens allowed
Descriptionfree proseLines after the heading until the next ##; concatenated into one string

A spec with no # System: heading, or with no ## Flow:, is an error.

Constants

Named values referenced by name in any value slot across all flows. Each constant is one -  line:

## Constants
- LARGE_ORDER = 100000
- LATE_DAYS = 30
- SALES_CHANNEL = "#sales"
- ACTIVE = true
PartRule
NameUPPER_SNAKE_CASE — [A-Z][A-Z0-9_]*
ValueInteger, "double-quoted string", or true / false

Each name must be unique. No expressions — literals only.

Entities

Persistent data shapes that flows can Query, Save, Update, and Delete. Each entity is one -  line:

## Entities
- order: order_id str, total int, charge_id str, status str
- invoice: invoice_id str, customer_email str, amount int, days_late int, status str

Field types

TypeMeaning
int32-bit signed integer
strUnicode string
booltrue or false
list of TList of another type, e.g. list of int, list of (sku str, amount int)
(f1 T1, f2 T2, ...)Inline record
<entity name>Another declared entity used as a nested type
  • Entity name: [a-z][a-z0-9_]*] — must be unique.
  • Field names must be unique within the entity.
  • The first field is the key — the only field required by Delete.
  • Save and Update require every field.

Services

External operations a flow can Call. Each service is one -  line with a signature:

## Services
- payments.charge(order_id str, amount int) -> (charge_id str, status str)
- inventory.reserve(sku str, qty int) -> (reserved bool)

Syntax: - <service>.<operation>(<params>) -> (<outputs>)

  • service and operation: [a-z][a-z0-9_]*
  • Params and outputs: comma-separated field type pairs, same types as Entities.
  • A service with multiple operations appears on separate lines.
  • Each service.operation pair must be unique.

Flows

A flow is the unit of compiled logic. Each starts with a ## Flow: heading followed by four header fields, then numbered steps.

## Flow: order_checkout
Intent: Reject empty orders, price the order, charge it, then confirm and save it.
Trigger: POST /orders with order_id str, customer_email str, tier str, items list of (sku str, amount int)
Mode: sync
Steps:
1. ...

Flow name: [a-z][a-z0-9_]* — unique across the spec.

Intent

Free prose describing the flow's purpose. Not compiled — shown in the Studio and stored as metadata.

Trigger

FormExample
HTTPPOST /orders with order_id str, amount int
Eventevent payment_received with invoice_id str, amount int
Scheduleschedule "0 2 * * *" with run_date str
Topictopic invoice.reminder with invoice_id str
  • HTTP methods: GET, POST, PUT, DELETE. Path starts with /.
  • with <fields> is optional when the trigger carries no payload.
  • Payload fields are accessed as input.<field>, or just <field> when unambiguous.

Mode

  • sync — the trigger waits for the flow; only valid for HTTP. Use with Respond with.
  • async — fire and forget; required for schedule, event, and topic.

Steps

The Steps: line ends the header. What follows is a numbered list (1., 2., ...). Sub-steps under If or In parallel are lettered (a., b., ...). Numbering must be sequential — gaps are an error.

An optional title goes in [square brackets] before the keyword: 1. [Check items] Validate: .... Steps can continue onto the next line if indented. The Tab key in the editor inserts three spaces.

Validate

Checks a condition and stops the flow if it fails.

Validate: <condition>. Otherwise stop with error "<msg>" [, responding with <fields>] Validate: <condition>. Otherwise fail with "<msg>"
1. [Has items?] Validate: `len(items) > 0`. Otherwise stop with error "order has no items".
2. Validate: `amount > 0`. Otherwise stop with error "bad amount", responding with order_id.
3. Validate: `active`. Otherwise fail with "account is inactive".
  • Otherwise stop — sync. Sends an error response with reason field.
  • responding with order_id, total — adds extra fields alongside reason.
  • Otherwise fail — async variant; no response body.

Compute

Assigns named computed values accessible later as <name>.<var>.

Compute <name>: - <var>: <value> - <var>: <value>
2. [Price it] Compute pricing:
   - subtotal: `sum(items.amount)`
   - discount: `subtotal / 10 if tier == "gold" else 0`
   - total: `subtotal - discount`
  • Name must be unique. Variables computed in declaration order; later ones can reference earlier ones.
  • Access results as pricing.subtotal, pricing.total, etc.
  • A Compute step with no -  lines is an error.

Call

Invokes an external service operation declared under ## Services.

Call <service>.<op> [as <name>] [with <args>] [. Retry N time(s).] [. On failure stop with error "<msg>" [, responding with <fields>].]
3. [Charge] Call payments.charge with order_id, amount = pricing.total. Retry 2 times. On failure stop with error "payment failed", responding with order_id.
4. Call inventory.reserve as res with sku = item.sku, qty = 1.
ClauseNotes
as <name>Names the call's outputs; defaults to the operation name
with paramShorthand for with param = param
with param = valueExplicit argument binding
Retry N time(s)0–3 retries on transient failure
On failure stop with error "..."Stop the flow on permanent failure; optional responding with

Outputs are accessed as <name>.<field>, e.g. charge.charge_id.

Query

Loads a list of entity records from the store.

Query <entity> as <name> [where field = value, ...]
5. Query invoice as open_invoices where status = "open".
6. Query order as all_orders.
  • Result is a list. Use len(open_invoices), open_invoices.field (gives a list of field values), or Publish each over it.
  • Entity must be declared under ## Entities.
  • where filter accepts multiple field = value pairs, comma-separated.

Publish

Sends one or more messages to a topic (async fan-out).

Publish to topic "<name>": field = value, field = value, ... Publish each <list> to topic "<name>"
6. Publish to topic "order.placed": order_id = order_id, total = pricing.total.
7. Publish each open_invoices to topic "invoice.reminder".
  • First form — a single message with explicit fields.
  • Second form — one message per item in the list, with all fields of each record.
  • Topic name pattern: [a-z][a-z0-9_.-]*

If

Conditional branch with optional else clause.

If <condition>: a. <step> b. <step> Otherwise: a. <step>
4. [Large order?] If `pricing.total >= LARGE_ORDER`:
   a. [Alert sales] Slack SALES_CHANNEL: "Large order {order_id}: {pricing.total} cents".
Otherwise:
   a. Stop.
  • Otherwise: at the same indent as If holds the false branch; omitting it skips straight to the next step.
  • Both branches rejoin at the step after the If.
  • Sub-steps are lettered (a., b., ...) and can include any step type including nested If.

In parallel

Runs two or more sub-steps concurrently and waits for all to complete before continuing.

In parallel: a. <one step> b. <one step>
5. [Confirm] In parallel:
   a. Email customer_email: "Order {order_id} confirmed. Total: {pricing.total}".
   b. Save order: order_id, total = pricing.total, charge_id = charge.charge_id, status = "confirmed".
  • Each branch is exactly one step — no nested If or In parallel.
  • Branches cannot stop the flow, respond, or use On failure on a Call.
  • Outputs of parallel steps are not accessible in subsequent steps.
  • Requires at least two lettered sub-steps.

Save / Update / Delete

Persists entity records in the store.

Save <entity>: field = value, field = value, ... Update <entity>: field = value, field = value, ... Delete <entity> where <key_field> = value
9.  Save order: order_id, total = pricing.total, charge_id = charge.charge_id, status = "new".
10. Update invoice: invoice_id, status = "reminded".
11. Delete order where order_id = order_id.
OperationRequired fields
SaveEvery field (insert)
UpdateEvery field
DeleteFirst (key) field only, with where

Bare field is shorthand for field = field. Entity must be declared under ## Entities.

Notifications

Sends a message over a channel.

<Channel> <to>: <message>
12. Email customer_email: "Your order {order_id} is confirmed. Total: {pricing.total}".
13. Slack SALES_CHANNEL: "New order {order_id} from {customer_email}".
14. SMS phone_number: "Your code is {code}".
15. Webhook callback_url: "done".
ChannelTypical <to>
EmailAn email address field
SlackA channel constant like SALES_CHANNEL
SMSA phone number field
WebhookA URL field

Both <to> and <message> are value slots (name, path, template string, or backtick expression).

Respond with

Ends a sync flow with a success response. Only valid in Mode: sync.

Respond with field [= value], field [= value], ...
16. Respond with order_id, charge_id = charge.charge_id, total = pricing.total.
  • Bare field is shorthand for field = field.
  • Multiple fields are comma-separated.
  • Using Respond with in an async flow is an error.

Stop

Ends the flow. Three forms:

17. Stop.
18. Stop with error "not found".
19. Stop with error "payment failed", responding with order_id.
  • Bare Stop — ends with status ok.
  • Stop with error "..." — ends with status error; in sync flows sends a response with a reason field.
  • responding with adds extra fields to the error response.
  • A flow that falls off the end of its last step without an explicit end is implicitly stopped with ok.

Expressions

Any value slot (in Compute, Validate, If, response fields, etc.) accepts five forms:

FormExampleNotes
Name or pathorder_id, pricing.total, input.itemsResolves to a declared field
ConstantLARGE_ORDERUPPER_SNAKE_CASE
Integer literal42, -732-bit signed
String template"Order {order_id}: {pricing.total}"{name} interpolates; {{ / }} are literal braces
Exact expression`len(items) > 0`Backtick-wrapped; full expression language

Plain English prose is accepted but marks the slot as an intent — a placeholder the logic model fills in. The flow compiles structurally but cannot run until every intent is resolved.

Reduction modifiers

Chained after a reduction function (sum, count, min, max, product):

ModifierEffect

`sum(xs.v where > 0)`
`count(items each * 3 where even)`
`sum(range(1, 10) each squared)`

Screens

UI forms and list views layered on top of flows. Screens appear after all flows and are optional.

## Screen: checkout
Title: Place an Order
Shows: form for order_checkout
Fields:
- order_id "Order ID": generated
- customer_email "Email"
- tier "Tier"
Submit: Place order
After: Your order has been placed.
KeyRequiredNotes
Title:yesDisplay title of the screen
Shows:yesform for <flow> or list of <entity>
Fields:no- <field> "Label" [: generated] — one per line
Columns:no- <field> "Label" — for list screens
Actions:no- <name> "Label"
Submit:noSubmit button label
After:noMessage shown after success
Filter:noCondition to pre-filter a list view

Screen name: [a-z][a-z0-9_]* — unique across all screens. The generated marker on a field means the UI auto-generates that value (e.g. a UUID) rather than showing an input.
